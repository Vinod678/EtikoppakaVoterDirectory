## C. Future voter list import guide (adding a new ward)

The workflow below is exactly the one used for Wards 2, 3 and 4. Example: **Ward 5, GP serials 1477–1845.**

### C.0 One-time setup (Python tools)
Python 3.7 or newer. Install the three libraries into a private folder (nothing system-wide):

```
python -m pip install --target tools/.pylib -r tools/requirements.txt
```
(`PyMuPDF==1.22.5`, `openpyxl==3.1.2`, `Pillow==9.5.0`.) Below, `tools/.pylib` is the **first argument** of the
scripts that need it. `tools/sync_assets.py` finds it automatically.

### C.1 Place the source files
* PDF: `input/ward5_voters.pdf` (the official Telugu roll printout, same card layout as the others).
* English workbook (optional first draft): `input/Etikoppaka_Ward_5_Corrected_English.xlsx`.
  Any draft whose header row contains `GP Serial No.` (or `GP Voter Serial No.`), `Voter Name (English)`,
  `Relationship`, `Relative Name (English)`, `Voter Name (Telugu)`, `Relative Name (Telugu)` works.

### C.2 Register the ward — `tools/ward_config.py`
Add the ward to the loop at the bottom (first serial and the official male/female counts from the summary table on
page 2 of the GP roll; the full table for all 14 wards is on page 2 of `input/ward2_voters.pdf`):

```python
for _n, _first, _counts in ((3, 739, (179, 190)), (4, 1108, (186, 183)), (5, 1477, (176, 193))):
```
This gives the ward its paths: `output/ward_5/…`, asset JSON `wards/voters_ward_5.json`, photos `voter_photos/ward_5/`.
Every ward has 369 voters except Ward 14 (4798–5170, 373 voters). The loop computes the last serial as
`first + 368`, and the checks in `tools/build_dataset.py` expect 369 records (they would print `FAIL` for 373), so for
Ward 14 add an explicit `WARDS[14] = dict(... last=5170 ...)` entry and make those 369s use the ward's own count.

### C.3 Correct the English names — `tools/ward_corrections.py`
1. `python tools/ward_corrections.py tools/.pylib 5 audit`
   → backs up the draft once to `output/ward_5/Etikoppaka_Ward_5_first_pass_backup.xlsx` (never modified afterwards)
   and writes `output/ward_5/ward5_audit.txt`: per voter the draft names, the Telugu text with known PDF-extraction
   artefacts fixed, the relationship label printed on the card, similarity to the PDF text, mismatches
   (`TE-MISMATCH`, `REL`, `EPIC`, `HOUSE`) and spellings already used in Wards 2/11.
2. Write `tools/corrections/ward5.py` (copy `ward3.py` / `ward4.py` as a template) with
   `TOKENS` (word → spelling), `FIELDS` (whole English values), `TE_FIELDS` (Telugu read from a card image) and
   `UNCERTAIN` (serial → reason, shown as "Check original PDF").
3. `python tools/ward_corrections.py tools/.pylib 5 apply`
   → writes the corrected 7-column workbook `input/Etikoppaka_Ward_5_Corrected_English.xlsx` and
   `output/ward_5/ward5_corrections_log.csv`.

How text is handled:
* **Telugu** is kept as printed. Only the known text-layer artefacts are fixed automatically (duplicated vowel sign or
  anusvara, duplicated syllable after "ర్ర" such as `గుర్రంరం → గుర్రం`, stray zero-width joiners). Anything else is
  changed only via `TE_FIELDS` after looking at the card.
* **English**: readable transliteration in the established spellings (Ward 2 first, then Ward 11), e.g. Senapathi,
  Yerramsetti, Sennamsetti, Rayi (రాయి) / Raya (రాయ), Kotwal, Naidu, "Nageswara Rao" (Rao as a separate word),
  Tatabbayi, Appala Naidu. Printed word order is kept. Run the cross-ward check (C.8) before shipping.
* **Relationship** is always the label printed on the card (Father / Husband / Mother), otherwise "Not specified";
  it is never guessed.

If the ward comes with an already-correct 7-column workbook (like Ward 11), skip C.3.

### C.4 Extract the photographs — `tools/extract_photos.py`
```
python tools/xlsx_dump.py input/Etikoppaka_Ward_5_Corrected_English.xlsx build/xlsx_ward5.json
python tools/extract_photos.py tools/.pylib input/ward5_voters.pdf build/xlsx_ward5.json output/ward_5/voter_photos output/ward_5/voter_photos_manifest.csv - 5
```
Each card is found by the number printed after the GP-serial label (`గ్రా.పం.ఓ.జా.వ.సం.`); the one image inside the
card rectangle is saved as `<serial>.jpg` (original JPEG bytes, unchanged) or `<serial>.png` (lossless) — the voter →
photo link is the serial number. The script prints missing / duplicate serials, reused images and per-page counts.

### C.5 Build the JSON — `tools/build_dataset.py`
```
python tools/build_dataset.py tools/.pylib . build/xlsx_ward5.json 5
```
Names / relationship come from the workbook; **age, gender, house number, assembly serial and EPIC are read from
the PDF cards**; photos from the manifest. Writes `output/ward_5/voters_ward_5.json` and the review workbook
`output/ward_5/voters_review_ward_5.xlsx`. Every check must print `PASS`: 369 records, serials once each, every
photo present, EPIC and assembly serials unique, core fields present, official male/female counts, source files
unchanged.

### C.6 Copy into the app — `tools/sync_assets.py`
```
python tools/sync_assets.py 5
```
→ `app/src/main/assets/wards/voters_ward_5.json` and `app/src/main/assets/voter_photos/ward_5/` (oversized photos
resized as in A.3; log in `output/ward_5/asset_photo_optimization.csv`).

### C.7 How the ward appears in the app (no code change needed)
* `VoterRepository.sources()` lists `assets/wards/` and imports every `voters_ward_<1-14>.json`; the parser prefixes
  photo names with `ward_N/`. Voter ids are `ward × 100000 + serial`, so serials may repeat across wards safely.
* On the next app start `ensureImported()` imports only wards whose `meta.generated_at` / record count changed.
  The Home page reads its counts from the database, so the ward card switches from "No data imported" to "369 voters".
* Households: each ward whose dataset is new or changed is grouped automatically **once**
  (`HouseholdGrouper`, key `VERSION|generated_at|record_count`). Other wards are not touched. Manual corrections
  (`household_locks`) are always kept. Re-importing a ward that already exists (changed JSON) re-runs automatic
  grouping for that ward only — manual households and moved voters stay as they are.
* Favourites, visits, notes, tags, blocks and block labels are separate tables and are never changed by an import.

### C.8 Verify
* Cross-ward spelling check: compare the new ward's surnames with Wards 2/3/4/11 (same Telugu word → same English
  spelling) — the ad-hoc check used on 20 Nov 2026 printed every Telugu word spelled differently across wards.
* Unit tests: add one line to `DatasetIntegrityTest.kt`:
  `@Test fun ward5_complete_… () = checkWard(5, 1477, 176, 193)`
  and extend `AllWardsImportTest.kt` (it asserts the exact set of wards and the 1,476 total) and the total in
  `app/src/androidTest/.../UiSmokeTest.kt`.
* `gradlew.bat testDebugUnitTest` — all tests must pass.

### C.9 Build and install
```
gradlew.bat testDebugUnitTest assembleDebug assembleShareable
```
* Debug: `app/build/outputs/apk/debug/app-debug.apk`
* Shareable: `app/build/outputs/apk/shareable/app-shareable.apk`
* Raise `versionCode` (and `versionName`) in `app/build.gradle.kts` for every build you hand out.

### C.10 Upgrade without losing data
* Install **over** the existing app: `adb install -r <apk>` (or open the APK on the phone and choose *Update*).
  Never uninstall first — uninstalling deletes favourites, visits, notes, tags, blocks and households.
* The new APK must be signed with the **same key** as the installed one (section E.3).
* Before larger upgrades: *Settings → Backup & Restore → Create backup* (encrypted with a password you choose).

## E. Future development precautions

### E.1 Never delete
* `input/` (original PDFs and corrected workbooks) — the only source of the voter data.
* `output/` — original photos, manifests, review workbooks, correction logs and first-pass backups.
* `tools/` including `tools/corrections/` and `tools/ward_config.py`.

* The Android debug keystore `C:\Users\VinodYedla9\.android\debug.keystore` (see E.3) and any future release keystore.

### E.2 Database compatibility
* Do not change the Room schema without adding a `Migration` in `data/db/VoterDatabase.kt` (never use destructive
  migrations) and exporting the new schema JSON. Current version: **5**.
* The voter id formula (`ward × 100000 + serial`) and the asset file names are part of the stored data — do not change.
* Do not run `gradlew connectedAndroidTest` on a device that holds real data: it uninstalls the app afterwards.
  Use `adb install -r` + `adb shell am instrument …` instead.

### E.3 Signing and upgrades (no secrets in this document)
* **All installations so far** (the development emulator and the shareable APK) are signed with this PC's Android
  **debug key**: `C:\Users\VinodYedla9\.android\debug.keystore`, certificate SHA-256
  `46:50:7c:47:45:2f:c0:c9:3b:9d:ca:d0:a0:9b:fe:47:b9:77:a6:d1:e1:8f:13:2c:6c:52:8b:90:b7:34:b6:e2`.
  Android only installs an update when the signing key is the same, so **back up this keystore file**. If it is
  lost, testers can only install a new build after uninstalling (losing their local data).
* The `shareable` build type = release build (R8, not debuggable) signed with that debug key. Good for a few trusted
  testers; not suitable for public distribution.
* **Proper release signing** (recommended before handing the app to more people):
  1. Create a key once (outside the project folder), e.g.
     `keytool -genkeypair -v -keystore C:\Keys\etikoppaka-release.jks -alias etikoppaka -keyalg RSA -keysize 4096 -validity 10000`
  2. Create `keystore.properties` in the project root (it is git-ignored) with the keys
     `storeFile`, `storePassword`, `keyAlias`, `keyPassword`.
  3. `gradlew.bat assembleRelease` then produces a signed `app/build/outputs/apk/release/app-release.apk`.
  4. Keep the `.jks` file and its passwords safe forever (two backups); losing them means no further updates.
  * Switching from the debug key to the release key is a one-time **uninstall + install** for every tester. To keep
    their data: *Settings → Backup & Restore → Create backup* in the old app, install the new one, then *Restore*.
* Never put keystores or passwords in the project, in this document or in `build.gradle.kts`.

### E.4 Testing lessons from this cleanup
* The previous release configuration (`packageScope` limited to `androidx`/`kotlin` packages) built fine but the APK
  crashed at start-up. **Always run a clean install of a shrunk build** before sharing it.
* On an emulator, a temporary second user (`adb shell pm create-user …`) gives a clean environment — but installing
  a package for that user also replaces the app code for the main user (the data stays separate). Remove the user
  afterwards with `adb shell pm remove-user <id>`.
